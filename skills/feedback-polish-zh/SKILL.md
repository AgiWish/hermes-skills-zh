# 职场反馈润色 (feedback-polish-zh)

## When to Use

- "这句话太直接了，帮我改一下"
- "我想说 XX 但不知道怎么说不伤人"
- 绩效反馈、代码 Review 评论、邮件回复需要更专业的表达
- `/feedback-polish-zh [你想说的话]`

## Quick Reference

```
/feedback-polish-zh [原始表述]

可选参数：
  --tone=建设性     # 保留批评，改为建设性表达（默认）
  --tone=委婉       # 大幅软化，适合敏感场景
  --tone=直接       # 保持直接但去除攻击性
  --context=绩效    # 绩效评估场景
  --context=codereview  # 代码审查场景
  --context=邮件    # 邮件回复场景
```

## Procedure

1. **理解原始意图**
   - 核心反馈是什么？（事实 / 行为 / 影响）
   - 目的是什么？（帮对方改进 / 拒绝 / 表达不满）
   - 关系背景？（平级 / 上下级 / 跨部门）

2. **改写原则（SBI 框架）**
   - **S**ituation（情境）：在什么具体情况下
   - **B**ehavior（行为）：观察到的具体行为
   - **I**mpact（影响）：这个行为带来的影响

3. **输出对比格式**

```markdown
**原始表述**：
[引用原文]

**问题诊断**：
- [为什么这样说有问题：太情绪化 / 攻击性 / 模糊 / 失焦]

**润色后**：
[改写版本]

**改动说明**：
- [改动点1]：把"[原话]"改为"[新表述]"，因为 [原因]
- [改动点2]：...

**可选的更[委婉/直接]版本**：
[备选表述]
```

## 常见场景示例

**代码 Review**
- 原始：「这代码写的什么玩意，完全不可读」
- 润色：「这块逻辑比较复杂，可以考虑提取方法名或加注释，方便后续维护。」

**绩效反馈**
- 原始：「他总是拖延，影响团队」
- 润色：「在 [具体项目] 中，任务交付时间多次超出约定节点，影响了下游环节的推进，建议在时间管理上重点关注。」

## Pitfalls

- 不要把实质性批评全部删掉，润色不是掩盖问题
- 保留事实性描述，只软化情绪表达
- 不要生成空洞的"积极语言"代替真实反馈

## Verification

- [ ] 改写后核心意思没有丢失
- [ ] 去除了情绪化和攻击性词汇
- [ ] 包含具体行为描述，不是泛化评价
- [ ] 对方看了能知道需要做什么改变
